Part II: Measuring Algorithm Quality

The Three Dimensions of Algorithm Quality

Correctness

  • Does it solve the problem?
  • Are results accurate?
  • Does it handle edge cases?

Efficiency

  • Time: How long does it take?
  • Space: How much memory?

Maintainability

  • Can others understand it?

  • Can we audit decisions?

Policy reality: We often trade some efficiency for transparency and maintainability.

Approach 1: The Straightforward Method

# Method 1: Simple and clear
find_max_simple <- function(data) {
  max_rate <- data$unemployment_rate[1]  # Start with first value
  max_county <- data$county[1]
  
  for(i in 2:nrow(data)) {
    if(data$unemployment_rate[i] > max_rate) {
      max_rate <- data$unemployment_rate[i]
      max_county <- data$county[i]
    }
  }
  
  return(list(county = max_county, rate = max_rate))
}

# Test it
result1 <- find_max_simple(unemployment_data)
cat("Highest unemployment:", result1$county, "at", 
    scales::percent(result1$rate, accuracy = 0.1))
Highest unemployment: County 917 at 15.0%

Pros: Easy to understand, memory efficient, straightforward approach Cons: Requires writing a loop, more verbose than built-in functions

Approach 2: Using Built-in Functions

# Method 2: Leverage R's optimized functions
find_max_builtin <- function(data) {
  max_idx <- which.max(data$unemployment_rate)
  return(list(
    county = data$county[max_idx],
    rate = data$unemployment_rate[max_idx]
  ))
}

# Test it
result2 <- find_max_builtin(unemployment_data)
cat("Highest unemployment:", result2$county, "at", 
    scales::percent(result2$rate, accuracy = 0.1))
Highest unemployment: County 917 at 15.0%

Pros: Concise, leverages optimized code, less error-prone Cons: Less transparent about what’s happening internally

Approach 3: The Sorting Method

# Method 3: Sort first, then take the top
find_max_sort <- function(data) {
  sorted_data <- data %>%
    arrange(desc(unemployment_rate))
  
  return(list(
    county = sorted_data$county[1],
    rate = sorted_data$unemployment_rate[1]
  ))
}

# Test it
result3 <- find_max_sort(unemployment_data)
cat("Highest unemployment:", result3$county, "at", 
    scales::percent(result3$rate, accuracy = 0.1))
Highest unemployment: County 917 at 15.0%

Pros: Very readable, gives us sorted data as a bonus Cons: Does more work than necessary (sorts entire dataset)

Part III: Understanding Computational Complexity

Big O Notation: The Language of Efficiency

Big O describes how runtime grows as input size increases

Common Complexities

  • O(1): Constant time
  • O(log n): Logarithmic
  • O(n): Linear
  • O(n log n): Log-linear
  • O(n²): Quadratic
  • O(2ⁿ): Exponential

Policy Translation

  • O(1): Checking eligibility rules
  • O(log n): Finding a record in sorted database
  • O(n): Processing all applications once
  • O(n²): Comparing every pair of cases
  • O(2ⁿ): Trying all possible combinations

Critical insight: The difference between O(n) and O(n²) can mean the difference between real-time and overnight processing.

Complexity in Action: Sorting Algorithms

Let’s implement and compare two sorting approaches:

# Bubble Sort: O(n²) - compares every pair
bubble_sort <- function(x) {
  n <- length(x)
  # Outer loop: we need n-1 passes to sort n elements
  # Each pass moves the largest unsorted element to its correct position
  for(i in 1:(n-1)) {
    # Inner loop: compare adjacent pairs from start to end of unsorted portion
    # We use (n-i) because after i passes, the last i elements are already sorted
    for(j in 1:(n-i)) {
      if(x[j] > x[j+1]) {
        # Swap elements
        temp <- x[j+1]
        x[j+1] <- x[j]
        x[j] <- temp
      }
    }
  }
  return(x)
}

# Test sorting performance with different sizes
test_sorting_performance <- function(sizes) {
  results <- tibble()
  
  for(n in sizes) {
    # Create random data - ensure we have enough values to sample from
    max_val <- max(1000, n)  # Use at least 1000 or n, whichever is larger
    test_data <- sample(1:max_val, n)
    
    # Time bubble sort (O(n²))
    bubble_time <- system.time({
      bubble_sort(test_data)
    })["elapsed"]
    
    # Time R's built-in sort (O(n log n))
    builtin_time <- system.time({
      sort(test_data)
    })["elapsed"]
    
    results <- bind_rows(results, tibble(
      n = n,
      bubble_sort = bubble_time,
      builtin_sort = builtin_time
    ))
  }
  
  return(results)
}

Part IV: Policy-Relevant Algorithm Design

Case Study: Emergency Resource Allocation

Scenario: During a natural disaster, we need to allocate emergency supplies to affected areas.

Constraints: - Limited supplies (trucks, medical kits, food) - Different areas have different needs and priorities - Time is critical - Decisions must be auditable and fair

Algorithm design questions: 1. How do we prioritize areas? 2. How do we ensure fair distribution? 3. How do we handle real-time updates? 4. How do we make decisions transparent?

Algorithm 1: Simple Priority Queue

# Create sample emergency data
set.seed(123)
emergency_data <- tibble(
  area_id = paste("Area", LETTERS[1:10]),
  population = sample(1000:50000, 10),
  severity_score = sample(1:10, 10, replace = TRUE),  # 1 = low, 10 = critical
  distance_km = sample(5:100, 10),
  supplies_needed = sample(10:500, 10)
) %>%
  # Calculate priority score (higher = more urgent)
  mutate(
    priority_score = (severity_score * population) / distance_km,
    priority_rank = rank(-priority_score)  # Negative for descending order
  )

Simple Allocation Algorithm

# GREEDY ALLOCATION ALGORITHM
# Input: areas (tibble with priority_score, supplies_needed, etc.)
#        total_supplies (integer: total units available)
# Output: tibble with area_id, allocated, needed, priority_rank

allocate_supplies_simple <- function(areas, total_supplies) {
  
  # STEP 1: Sort areas by priority (highest priority first)
  # This creates our "queue" - we'll serve highest priority areas first
  sorted_areas <- areas %>%
    arrange(desc(priority_score))  # desc() = descending order
  
  # STEP 2: Initialize our tracking variables
  remaining_supplies <- total_supplies  # How many supplies we have left
  allocations <- tibble()              # Empty table to store results
  
  # STEP 3: Go through each area in priority order
  for(i in 1:nrow(sorted_areas)) {
    current_area <- sorted_areas[i, ]  # Get data for this area
    
    # STEP 4: Give this area as much as possible (but not more than needed)
    # Example: Area needs 500, we have 300 left → give 300
    # Example: Area needs 200, we have 300 left → give 200
    allocated_to_this_area <- min(current_area$supplies_needed, remaining_supplies)
    
    # STEP 5: Record what we gave to this area
    allocations <- bind_rows(allocations, tibble(
      area_id = current_area$area_id,           # Which area (character)
      allocated = allocated_to_this_area,       # How much we gave (integer)
      needed = current_area$supplies_needed,    # How much they needed (integer)
      priority_rank = current_area$priority_rank # Their rank (integer)
    ))
    
    # STEP 6: Update how many supplies we have left
    remaining_supplies <- remaining_supplies - allocated_to_this_area
    
    # STEP 7: If we're out of supplies, stop (no point continuing)
    if(remaining_supplies <= 0) break
  }
  
  # STEP 8: Add areas that got nothing (for complete reporting)
  # Find areas we never got to (ran out of supplies before reaching them)
  unallocated_areas <- sorted_areas %>%
    filter(!area_id %in% allocations$area_id) %>%  # Areas not in our results yet
    select(area_id, supplies_needed, priority_rank) %>%
    mutate(
      allocated = 0,                    # They got 0 supplies
      needed = supplies_needed          # Their original request
    ) %>%
    select(area_id, allocated, needed, priority_rank)  # Keep only the columns we want
  
  # STEP 9: Combine allocated and unallocated areas into final result
  final_allocations <- bind_rows(allocations, unallocated_areas)
  
  return(final_allocations)
}

Part V: Algorithm Design Principles for Policy

The Policy Algorithm Design Framework

1. Define Success Clearly - What outcomes matter most? Often referred to as KPIs. - How do we measure fairness? - What are acceptable trade-offs?

2. Consider Stakeholder Needs - Who is affected by decisions? - What information do they need? - How can they contest decisions?

3. Plan for Scale and Change - Will this work with 10x more data? - How do we handle new requirements? - Can we update the algorithm safely?

4. Build in Accountability - Can we explain every decision? - Can we audit the process? - How do we detect and fix problems?

Common Algorithmic Patterns in Policy

Matching Problems

  • Examples: School assignment, organ donation, job placement
  • Key considerations: Stability, fairness, efficiency
  • Typical complexity: O(n²) to O(n³)

Optimization Problems

  • Examples: Budget allocation, route planning, scheduling
  • Key considerations: Multiple objectives, constraints
  • Typical complexity: Often NP-hard, need approximations

Classification Problems

  • Examples: Fraud detection, risk assessment, eligibility
  • Key considerations: False positive/negative rates, bias
  • Typical complexity: O(n) for prediction, varies for training

Search and Retrieval

  • Examples: Finding records, matching cases, recommendations
  • Key considerations: Accuracy, speed, privacy
  • Typical complexity: O(log n) with good indexing

When Simple Algorithms Win

Policy contexts often favor simple approaches because:

  • Transparency: Stakeholders can understand the logic
  • Auditability: Easier to verify correct implementation
  • Maintainability: Fewer bugs, easier to modify
  • Fairness: Less likely to have hidden biases
  • Robustness: Fail gracefully, predictable behavior

Example: Linear scoring models vs. complex ML for benefit eligibility - Linear model: Each factor has clear weight, easy to explain - Complex ML: Might be more accurate but creates “black box” decisions

Important

Policy principle: Choose the simplest algorithm that meets your accuracy and fairness requirements.

Algorithm Documentation Template

Essential documentation for policy algorithms:

## Algorithm: Emergency Supply Allocation

### Purpose
Allocate limited emergency supplies to affected areas during disasters

### Inputs
- Area data: population, severity, distance, needs
- Available supplies: total units available

### Logic
1. Calculate priority score: (severity × population) / distance
2. Sort areas by priority (highest first)  
3. Allocate supplies greedily until exhausted

### Assumptions
- Higher population areas need proportionally more supplies
- Closer areas can be served more efficiently
- Severity scores are accurate and comparable

### Limitations
- Does not consider supply chain constraints
- May not achieve optimal global allocation
- Assumes all supply units are equivalent

### Testing
- Verified with historical disaster data
- Stress tested with 10,000+ areas
- Edge cases: no supplies, no areas, invalid data
